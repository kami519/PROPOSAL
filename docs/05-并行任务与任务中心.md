## 1. 背景与问题

### 1.1 用户诉求

用户的原话是：

> 有些时候想要进行下一个视频的总结可能得等很久而且很麻烦，所以我希望能够并行任务。

实际使用场景是：

1. 粘贴视频 A，点「AI 视频总结」。
2. A 没有字幕，需要下载音频并用本地 Whisper 转写，可能等几分钟。
3. 此时想处理视频 B，只能重新粘贴链接并解析。
4. 一旦解析 B，A 的结果页被替换，A 的总结面板消失；A 的后台任务还在跑，但界面上已经找不到它。
5. 用户只能等，或者去笔记仓库里翻「整理中」的草稿；没有进度、没有完成提醒、没有取消和重试。

所以痛点不只是「慢」，而是 **慢 + 任务不可见 + 切换麻烦 + 无法并行**。

### 1.2 代码层面的根因

#### 后端：并发被三处串行限制

| 位置 | 现状 | 影响 |
| --- | --- | --- |
| `backend/config.py` 的 `SUMMARY_WORKERS` | 默认 1 | 所有总结任务在同一个线程池里排队，第二个任务必须等第一个的总结阶段结束 |
| `backend/summary.py` 的 `_transcribe_lock` | 全局互斥锁 | 即使调大 `SUMMARY_WORKERS`，Whisper 转写仍然一次只能跑一个 |
| `backend/summary.py` 的 `_article_executor` | `max_workers=1` | 多个任务完成后，完整文案只能逐个生成 |

此外还有四个工程问题：

- `SummaryStore` 没有任务列表、取消、重试接口；任务只能按 ID 查询。
- 没有「同一个 URL 正在跑就复用」的去重。批量加入时可能重复调用模型、重复写同一篇笔记。
- `_jobs` 只增不减，没有 TTL；批量任务会放大内存占用。
- `_chat` 没有对 `429 / 5xx / 超时` 做重试退避；并发一开更容易直接失败。

#### 前端：状态只活在当前面板里

- `SummaryPanel` 自己持有 `job`、`timer`、`generation`，组件卸载时 `stopPolling()` 生效。
- `Downloader` 开始解析下一个链接时会清空 `result`，`ResultWorkbench` 与 `SummaryPanel` 随之卸载，轮询停止。
- 任务 ID 没有写入 URL 或 localStorage，刷新页面后无法回到正在跑的任务。
- 没有任务列表、完成提醒、取消/重试入口。
- `extractVideoUrl()` 只提取第一条链接，没有批量输入能力。

### 1.3 结论

只把 `SUMMARY_WORKERS` 从 1 调到 3 不够。必须同时补齐：

1. **资源分级并发**：LLM 可以并行，Whisper 按 CPU 能力串行/少量并行，文案独立并行。
2. **任务生命周期接口**：列表、取消、重试、去重、TTL。
3. **前端任务中心**：把任务状态从组件里提出来，与页面解耦。
4. **持久化**：刷新页面不丢；服务重启后历史可查，运行中任务可重试。

## 2. 目标与非目标

### 2.1 目标

1. **并行执行**：多个视频的总结可以同时排队和执行，不再被单线程池和全局转写锁卡死。
2. **任务与页面解耦**：关闭面板、刷新页面、去解析下一个视频，都不会停止或丢失正在跑的任务。
3. **可见可控**：任务中心能看到每个任务的阶段、进度、队列位置，能取消、重试、打开结果。
4. **可恢复**：同一视频不重复烧 token；失败重试复用已完成的转写缓存；服务重启后历史可查。
5. **保持轻量部署**：仍然单进程 FastAPI + 本地文件 + SQLite 索引，不引入 Celery、Redis、消息队列。
6. **不破坏现有下载链路**：下载、暂停、继续、取消、笔记仓库的行为保持不变。

### 2.2 非目标（本轮不做）

- 不改下载任务的 UI；下载仍然只跟踪当前一条。
- 不做「批量下载 + 批量总结」一条龙。
- 不做队列暂停/恢复、优先级、置顶、定时执行。
- 不做多用户、登录、权限、云端同步。
- 不做服务端 Web Push；只在浏览器本地做 Toast、标题角标和可选的桌面通知。
- 不改总结 prompt、模型和笔记 Markdown 结构。
- 不把 SQLite 扩展成完整任务数据库；任务元数据用 JSON 快照。

## 3. 已确认决策

| 决策项 | 选择 | 说明 |
| --- | --- | --- |
| 本轮范围 | 只做 AI 总结并行 + 任务中心 | 下载流程不动，控制风险 |
| 任务持久化 | 页面刷新保留 + 服务重启保留历史 | localStorage + 服务端 JSON 快照 |
| 批量方式 | 先并行解析标题，再逐条入队 | 笔记标题、封面、UP 主、时长准确 |
| 开发节奏 | 已按本文档实施 | 代码、测试、文档已同步更新 |

## 4. 总体方案

### 4.1 核心思路

```text
浏览器
  ├─ 首页：单条解析 → AI 总结入口
  ├─ 任务中心：#/tasks
  │    ├─ 批量粘贴链接
  │    ├─ 任务卡片（排队 / 转写 / 总结 / 文案 / 完成 / 失败）
  │    └─ 详情：#/tasks/{id}
  └─ 笔记仓库：#/library（长期结果）

FastAPI
  ├─ SummaryStore：任务注册表 + 生命周期
  ├─ 任务执行器：最多 3 个任务同时推进
  ├─ 转写信号量：默认 1 路 Whisper
  ├─ LLM 信号量：最多 4 个模型请求
  ├─ 文案执行器：最多 2 个整理稿任务
  ├─ summary-cache：转写 / 总结 / 文案缓存
  ├─ Markdown 笔记：任务开始即建草稿，完成后原子落盘
  └─ summary-jobs.json：任务元数据快照
```

「任务中心」是工作台，「笔记仓库」是结果库：

- 任务中心负责「现在跑到哪了、能不能取消、失败了怎么重试」。
- 笔记仓库负责「已经整理好的 Markdown、摘要、完整文案、原始转写」。
- 任务完成后仍然自动写入笔记仓库，不新增第二套结果存储。

### 4.2 并发模型

| 资源 | 默认并发 | 配置项 | 理由 |
| --- | --- | --- | --- |
| 总结任务整体 | 3 | `SUMMARY_WORKERS` | 同时推进多个视频；受队列上限约束 |
| Whisper 转写 | 1 | `SUMMARY_TRANSCRIBE_WORKERS` | CPU 密集；默认串行，避免 3 路转写把 CPU 和内存打满 |
| LLM 请求 | 4 | `SUMMARY_LLM_CONCURRENCY` | 总结 + 文案共享；网络 IO，可并行 |
| 完整文案 | 2 | `SUMMARY_ARTICLE_WORKERS` | 文案是独立后台任务，不必占住总结线程 |
| 活跃任务上限 | 20 | `SUMMARY_QUEUE_MAX` | 防止一次粘贴过多链接导致磁盘/内存/API 失控 |

资源分级的意义：

- **有字幕的视频**：不下载音频，直接走 LLM，3 个任务可以真正并行。
- **无字幕的视频**：音频下载可以重叠，Whisper 转写按 1 路排队；转写完成后，LLM 总结可以与下一个视频的转写重叠。
- **长视频**：总结先返回，文案在后台继续；多个文案可以并行整理。
- **不会无限开线程**：任务数、LLM 请求数、转写数、文案数都有上限。

> 已知取舍：当前实现是「一个任务占用一个总结线程，直到整个总结阶段结束」。如果某个任务在等 Whisper 信号量，它会占住 3 个总结线程中的一个。默认 3 路仍然能给字幕类任务留下 2 路；如果实测发现阻塞明显，后续可把总结执行器拆成「字幕/转写/总结」三段流水线。本轮先不引入更复杂的阶段队列。

### 4.3 关键流程

#### 单条总结

```text
视频解析结果 → 点「AI 视频总结」
  → 创建 summary job
  → 任务中心出现一条任务
  → 首页面板显示进度；关闭面板任务继续
  → 完成 Toast + 标题角标
  → 任务卡片可打开详情 / 笔记
```

#### 批量总结

```text
任务中心粘贴多条链接
  → 前端提取并去重 URL（最多 12 条）
  → 最多 3 条同时解析标题、封面、时长
  → 每解析完一条，立即创建 summary job
  → 任务中心逐条显示「解析中 → 排队中 → 转写/总结中」
  → 可继续去首页解析下一条，页面关闭也不影响已入队任务
```

#### 刷新 / 重启

```text
刷新页面
  → localStorage 恢复任务 ID 与展示信息
  → GET /api/summaries?ids=... 拉取服务端最新状态
  → 继续轮询进行中的任务

服务重启
  → 启动时读取 summary-jobs.json
  → 运行中的任务标记为「已中断，可重试」
  → 已完成任务从 summary-cache / 笔记恢复展示
  → 用户点重试，复用已有转写缓存
```

## 5. 后端设计

### 5.1 配置项

在 `backend/config.py` 新增，并同步 `.env.example`：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `SUMMARY_WORKERS` | `3` | 同时推进的总结任务数，替代现在的默认 1 |
| `SUMMARY_TRANSCRIBE_WORKERS` | `1` | Whisper 并发路数；CPU 上建议 1，GPU/强 CPU 可调 2 |
| `SUMMARY_LLM_CONCURRENCY` | `4` | LLM 请求总并发上限 |
| `SUMMARY_ARTICLE_WORKERS` | `2` | 完整文案并行数，替代现在的固定 1 |
| `SUMMARY_QUEUE_MAX` | `20` | 活跃任务上限；超出返回 `SUMMARY_TOO_BUSY` |
| `SUMMARY_JOB_TTL_SECONDS` | `86400` | 任务中心历史保留时间，默认 24 小时 |
| `SUMMARY_MAX_JOBS` | `100` | JSON 快照最多保留任务数 |
| `SUMMARY_LLM_RETRIES` | `2` | 429 / 5xx / 超时重试次数 |
| `SUMMARY_LLM_BACKOFF_SECONDS` | `1.5` | 指数退避基数，实际等待加随机抖动 |
| `SUMMARY_PERSIST_JOBS` | `true` | 是否写 `summary-jobs.json` |

说明：

- `SUMMARY_WORKERS` 是「任务级」并发，不是「LLM 请求级」并发；两者分别控制。
- `SUMMARY_TRANSCRIBE_WORKERS` 大于 1 时，每个转写都会完整解码音频到内存。1 小时音频约 230 MB float32，开 2 路就要预留约 460 MB，外加 Whisper 模型本身。默认 1 是安全值。
- 队列上限只统计活跃任务（`queued / processing / cancelling`），已完成历史不计入。

### 5.2 任务模型

在现有 `SummaryJob` 上增加：

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `uploader` | `str \| None` | 笔记元数据、任务卡片展示 |
| `queue_position` | `int` | 等待执行器空位时的队列序号；已开始为 0 |
| `transcribe_queue_position` | `int` | 等待 Whisper 信号量时的队列序号；不在等待为 0 |
| `started_at` | `float \| None` | 开始执行时间 |
| `finished_at` | `float \| None` | 结束时间 |
| `cancel_requested` | `bool` | 协作式取消标记，不对外直接暴露 |
| `retry_count` | `int` | 重试次数，便于排障 |
| `deduped` | `bool` | 本次创建是否复用了已有任务 |

任务状态：

| 状态 | 含义 |
| --- | --- |
| `queued` | 已创建，等待执行器线程 |
| `processing` | 正在执行，具体阶段看 `stage` |
| `cancelling` | 已请求取消，正在停止 |
| `cancelled` | 已停止并清理 |
| `done` | 总结完成；文案可能仍在后台生成 |
| `error` | 失败 |

任务阶段：

| 阶段 | 含义 |
| --- | --- |
| `queued` | 排队 |
| `fetching_subtitles` | 提取平台字幕 |
| `downloading_audio` | 下载音频流 |
| `waiting_transcription` | 等待 Whisper 槽位 |
| `transcribing` | 本地转写 |
| `summarizing` | 调用模型生成结构化总结 |
| `done` | 总结完成 |
| `cancelling` | 正在取消 |
| `cancelled` | 已取消 |

文案状态单独维护：`idle / processing / done / error / cancelled`，不复用总结状态。

### 5.3 执行器与信号量

```python
# 伪代码
_summary_executor = ThreadPoolExecutor(max_workers=SUMMARY_WORKERS)
_article_executor = ThreadPoolExecutor(max_workers=SUMMARY_ARTICLE_WORKERS)
_transcribe_slots = threading.BoundedSemaphore(SUMMARY_TRANSCRIBE_WORKERS)
_llm_slots = threading.BoundedSemaphore(SUMMARY_LLM_CONCURRENCY)
```

- 任务提交到 `_summary_executor`，队列由 `ThreadPoolExecutor` 自身维护。
- `transcribe_audio()` 在 `_transcribe_slots` 内完成「解码音频 + 模型转写」；这样内存峰值受控。
- `_chat()` 在 `_llm_slots` 内发起请求；重试等待时释放槽位，避免占着并发额度睡觉。
- 文案任务提交到 `_article_executor`，不占总结执行器线程。
- 所有共享数据结构继续使用 `SummaryStore._lock`（`RLock`）保护；`public()` 在锁内读取，避免并发下读到半更新状态。

### 5.4 去重与缓存

#### 同 URL 活跃去重

`SummaryStore` 增加 `_active_by_url: dict[str, str]`：

- 创建任务前，先查这个 URL 是否已有活跃任务。
- 有则直接返回已有任务的 `public()`，并标记 `deduped=true`，不重复建笔记、不重复调模型。
- 任务进入终态（`done / error / cancelled`）时，从映射中移除。

#### 缓存命中

现有三级缓存保持不变：

- `load_cached_transcript(url)`：转写缓存。
- `load_cached_summary(url)`：总结缓存。
- `load_cached_article(url)`：文案缓存。

创建任务时：

1. 先查总结缓存；命中则直接返回 `done`，并把结果写入笔记（如果笔记不存在或需要补全）。
2. 没有总结缓存但有转写缓存时，任务跳到「总结」阶段，不再重新下载/转写。
3. 都没有才进入完整流程。

#### 笔记写入顺序

当前 `create()` 在查缓存前就 `prepare_note()`。批量场景下要调整为：

1. 先做 URL 去重和缓存判断。
2. 需要真正执行时，再 `prepare_note()`、创建 `NoteWriter`、启动草稿。
3. 缓存命中且已有完成笔记时，不重置笔记状态，直接返回结果和 `noteId`。

这样可以避免「命中缓存还把笔记短暂改成 processing」以及并发写同一篇笔记。

### 5.5 取消

新增 `SummaryCancelled` 异常和 `POST /api/summaries/{id}/cancel`。

协作式取消点：

| 阶段 | 取消点 |
| --- | --- |
| 等待执行器 | `future.cancel()` 成功则立即取消；失败则设置标记，等任务启动时检查 |
| 提取字幕 | 调用前、调用后检查；字幕提取本身通常很快，不强行中断 |
| 下载音频 | yt-dlp progress hook 检查，命中则抛 `SummaryCancelled` |
| 等待 Whisper | 使用带超时的 `acquire` 循环，每 0.5 秒检查取消标记 |
| 转写 | 每个 segment 前检查；命中则关闭生成器并抛出 |
| 总结 | 每个分段调用前、最终调用前后检查 |
| 文案 | 每个分段调用前检查 |

限制：

- LLM HTTP 请求一旦发出，无法真正中断；取消会标记 `cancelling`，等当前请求返回后停止后续步骤。最长等待时间等于 `SUMMARY_TIMEOUT_SECONDS`（默认 120 秒）。
- 取消后：
  - 临时目录 `data/cache/summaries/<id>` 删除。
  - 笔记草稿保留，状态改为 `cancelled`，错误信息写「任务已取消，可重新生成」。
  - 任务状态 `cancelled`，`canRetry=true`。
  - 已产生的转写缓存保留，重试可复用。
- 总结已完成但文案仍在生成时，取消只停止文案（`articleStatus=cancelled`），总结结果和笔记摘要保留；用户仍可查看总结，之后用文案接口重新整理。

### 5.6 重试

新增 `POST /api/summaries/{id}/retry`，只允许 `error` 或 `cancelled` 状态。

采用「原地重置同一个 job」而不是新建任务，原因：

- 任务中心 ID 稳定，用户点重试后卡片不会跳成新的一条。
- 笔记按 `source_url` 去重，原本就是同一篇。
- 转写缓存、已有 `transcript` 可以直接复用。

重置内容：

- `status=queued`、`stage=queued`、`progress=0`。
- 清空本次的 `error / errorCode / result / article / articleStatus`。
- 保留 `url / title / thumbnail / platform / uploader / duration / noteId / transcript / transcriptSource`。
- `cancel_requested=false`，`retry_count += 1`。
- 重新 `prepare_note()` + `NoteWriter.start()`，重新提交执行器。

文案单独失败不调用这个接口；继续使用现有的 `POST /api/summaries/{id}/article` 重新整理。

### 5.7 任务列表接口

新增：

```http
GET /api/summaries?ids=<id1,id2>&status=&limit=50
```

规则：

- `ids` 可选；不传时返回最近任务（用于服务端历史）。
- `status` 可选：`active / queued / processing / done / error / cancelled`。
- 列表项**不返回完整 `result`**，只返回：
  - 基础信息：`id / url / title / thumbnail / platform / uploader / duration`
  - 状态：`status / stage / progress / queuePosition / transcribeQueuePosition`
  - 结果摘要：`hasResult / tldr / noteId / articleStatus / articleProgress / articleChars / articleError`
  - 能力：`canCancel / canRetry / deduped`
  - 时间：`createdAt / updatedAt / startedAt / finishedAt`
- 详情仍走 `GET /api/summaries/{id}`，返回完整 `result`。

```json
}
```

### 5.8 持久化

任务元数据写入 `data/cache/summary-jobs.json`。

写入时机：

- 任务创建。
- 任务进入终态（`done / error / cancelled`）。
- 取消、重试、服务关闭。
- 不按进度每秒写，避免频繁磁盘 IO。

写入内容（只存元数据，不存完整 result/transcript/article）：

```json
{
  "version": 1,
  "savedAt": 1761650000,
  "jobs": [
    {
      "id": "0f8c...",
      "url": "https://...",
      "title": "从零开始认识显卡",
      "thumbnail": "https://...",
      "platform": "B站",
      "uploader": "硬件茶谈",
      "duration": 919,
      "status": "done",
      "stage": "done",
      "progress": 100,
      "noteId": "note_1130ec1aedb0",
      "error": null,
      "errorCode": null,
      "createdAt": 1761650000,
      "updatedAt": 1761650100
    }
  ]
}
```

启动加载规则：

- 最多保留 50 条，按 `updatedAt` 倒序；活跃任务优先保留。
- `queued / processing / cancelling`：说明上次进程没跑完，标记为 `error`：
  - `errorCode=SUMMARY_INTERRUPTED`
  - `error=服务重启，任务已中断，请重试。`
  - 保留 `noteId`、`url`、标题，`canRetry=true`。
  - 同步把对应笔记状态改为 `error`（如果仍是 processing）。
- `done`：尝试从 `load_cached_summary(url)` 恢复 `result / article / transcriptSource`；缓存过期则保留任务卡片并提示「结果已过期，可查看笔记或重新生成」。
- `error / cancelled`：直接恢复展示。
- 原子写入：先写 `.tmp`，再 `replace()`；读失败时记录日志并忽略，不阻塞启动。
- 服务正常关闭时，把仍在活跃状态的任务标记为中断（或禁止新任务），写一次快照，再关闭执行器；避免下次启动把它们当成未知状态。

页面刷新由前端 localStorage 负责；服务端 JSON 负责跨服务重启。两者合并时，以服务端状态为准。

### 5.9 LLM 可靠性

`_chat()` 改造：

- 新增 `should_cancel` 可选参数，在请求前后检查取消。
- 对以下情况重试：
  - `429 Too Many Requests`
  - `500 / 502 / 503 / 504`
  - `httpx.TimeoutException`
  - `httpx.ConnectError`
- 不重试：
  - `400 / 401 / 403 / 404 / 422`
  - JSON 格式错误（继续走现有的修复 + 降级路径）
- 等待策略：
  - `retry_index` 从 0 开始。
  - 基础等待 `SUMMARY_LLM_BACKOFF_SECONDS * 2^retry_index`。
  - 加 0~0.5 秒随机抖动。
  - 如果响应带 `Retry-After`，优先使用该值，并设置上限（例如 30 秒）。
- 每次重试记录日志：`job_id / status_code / attempt / wait`。
- 重试耗尽后返回现有 `SUMMARY_API_ERROR`，错误文案补充「AI 服务繁忙，已重试 N 次」。
- 继续记录 `finish_reason`、`reasoning_content` 长度，便于排查空 content。

本轮仍建议每次调用使用独立 `httpx.Client`（现有做法），不引入共享连接池生命周期问题；并发 4 路时连接建立开销可以接受。

### 5.10 清理

新增后台清理线程（与 `JobStore` 的清理线程类似）：

- 每 60 秒执行一次。
- 删除超过 `SUMMARY_JOB_TTL_SECONDS` 的终态任务（`done / error / cancelled`）。
- 删除 `data/cache/summaries/` 下超过 TTL 的孤儿目录（崩溃残留）。
- 任务数量硬上限 100；超出时优先删除最旧的终态任务。
- `summary-cache` 仍按现有 `SUMMARY_CACHE_TTL_SECONDS` 清理，不在任务中心删除。

### 5.11 笔记与仓库状态

新增「已取消」状态，避免取消后笔记显示成「失败」：

- `NoteWriter` 增加 `cancel(message)`：
  - 草稿 frontmatter 写 `status: cancelled`、`error: 任务已取消...`。
  - 不执行最终改名，保留 `.drafts/` 草稿。
  - SQLite 索引 `status=cancelled`。
- `LibraryStore.content_path()` 的草稿可见条件加入 `cancelled`。
- 前端 `LibraryStatus` 增加 `cancelled`，仓库筛选和状态徽标增加「已取消」。
- 服务重启时，`LibraryStore.__init__` 仍负责把遗留 `processing` 笔记标记为 `error`；`SummaryStore` 加载快照时再补一次中断信息，二者不冲突。

## 6. 前端设计

### 6.1 全局任务状态

新增 `frontend/src/context/SummaryQueueContext.tsx`，放在 `ToastProvider` 内、`App` 外。

职责：

- 维护任务列表。
- 统一轮询活跃任务。
- 处理 localStorage 恢复。
- 处理完成/失败通知。
- 提供 `enqueue / enqueueMany / cancel / retry / dismiss / getTask / findByUrl`。

任务类型：

```ts
export type SummaryTaskStatus =
  | 'analyzing'   // 仅前端，批量解析阶段
  | 'queued'
  | 'processing'
  | 'cancelling'
  | 'cancelled'
  | 'done'
  | 'error'

export interface SummaryTask extends Omit<SummaryJob, 'status'> {
  status: SummaryTaskStatus
  url: string
  uploader?: string | null
  queuePosition?: number
  transcribeQueuePosition?: number
  canCancel?: boolean
  canRetry?: boolean
  hasResult?: boolean
  tldr?: string
  deduped?: boolean
  clientId?: string
  addedAt?: number
  localError?: string | null
}
```

localStorage：

- key：`clipdock.summary.tasks.v1`
- 只存任务 ID、URL、标题、封面、平台、UP 主、时长、创建时间、最近状态。
- 不存 `result / article / transcript`，避免 localStorage 膨胀。
- 最多 30 条，超过时删除最旧的终态任务。
- 读取时做结构校验；坏数据直接丢弃。

轮询：

- 只在存在「活跃任务」或「文案 processing」时启动。
- 每 1.2 秒调用一次 `GET /api/summaries?ids=...`，一次请求拿全部活跃任务。
- 网络失败退避：1.2 秒 → 3 秒 → 5 秒，避免断网时刷屏。
- 页面隐藏时降频到 5 秒；页面重新可见时立即拉一次。
- 任务全部进入终态后停止轮询；详情页打开时单独拉一次完整详情。
- 用 `inFlight` 标记防止请求叠加。

状态迁移通知：

- 记录上一次状态；只有 `active → done` 时提示「《标题》总结完成」。
- `active → error` 提示失败原因。
- 初次从 localStorage 恢复时不提示，避免刷新后重复弹 Toast。
- 完成时同步更新 `document.title` 为 `(2) 收片 ClipDock`；活跃任务为 0 时恢复原标题。

可选桌面通知：

- 任务中心提供「桌面通知」开关，默认关闭。
- 用户主动点击时请求 `Notification.requestPermission()`。
- 只在 `document.hidden` 且权限为 granted 时发系统通知。
- 局域网 HTTP 下浏览器可能禁用 Notification；页面提示「localhost / HTTPS 可用」。
- 无论通知是否成功，Toast 和标题角标始终生效。

多标签页说明：

- 两个标签页会各自轮询、各自弹完成提示；本轮接受这个限制。
- 后续如需要，可用 `BroadcastChannel` 让一个标签页负责轮询和通知。

### 6.3 批量解析与入队

`frontend/src/lib/format.ts` 增加：

```ts
export function extractVideoUrls(text: string): string[]
```

规则：

- 同时匹配完整 `https://...` 和裸域名链接。
- 按出现顺序返回，去重。
- 清洗尾部中文标点和分享文案。
- 单次最多取 12 条；超出提示用户分批。

批量流程：

1. 用户在任务中心粘贴多条链接。
2. 前端实时显示「识别到 N 个链接」。
3. 点「加入并行队列」。
4. 前端为每条链接创建本地行：`status='analyzing'`。
5. 用 3 个并发 worker 调用 `POST /api/analyze`：
   - 成功：拿到 `title / thumbnail / platform / uploader / duration / webpageUrl`。
   - 立即调用 `POST /api/summaries` 创建任务。
   - 用服务端返回的 job 替换本地行。
   - 失败：本地行标记 `error`，显示错误信息和「重试解析」。
6. 每解析完一条就入队一条，不等待全部解析完。
7. 已有相同 URL 的活跃/完成任务时跳过，并提示「已跳过重复链接」。

限制与提示：

- 解析阶段依赖页面保持打开；一条通常 3–15 秒，最多 3 条并行。
- 入队成功后，页面可以关闭，任务在服务端继续跑。
- 如果用户一次粘贴超过 12 条，提示分批；不静默截断。

> 本轮选择「先解析再入队」是为了让笔记标题、封面、UP 主、时长准确。代价是解析阶段需要页面在。若后续想做到「粘贴即入队、标题后台补全」，需要让总结任务自己 probes 元数据并处理笔记重命名，另行设计。

## 7. 关键页面流程

### 7.1 单条总结并切换下一个

```text
首页解析 A → 点 AI 总结
  → 任务中心出现 A（processing）
  → 用户点「继续收下一个」
  → 粘贴 B、解析 B
  → A 面板卸载，但 A 任务仍在任务中心轮询
  → B 点 AI 总结，任务中心出现 B
  → A 完成时 Toast + 标题角标
  → 点 A 卡片 → 详情/笔记
```

### 7.2 批量三条

```text
任务中心粘贴 3 条链接 → 加入并行队列
  → 3 条先解析（最多 3 并发）
  → 第一条解析完立即创建 job；其余继续解析
  → 任务卡片：排队中 / 转写中 / 总结中
  → 有字幕的两条并行总结
  → 无字幕的一条等待 Whisper，转写完成后与下一条总结重叠
  → 完成逐条 Toast；任务卡片显示 tldr
```

### 7.3 刷新页面

```text
轮询中 → F5
  → Provider 从 localStorage 恢复 3 条任务
  → GET /api/summaries?ids=... 合并服务端状态
  → 继续轮询，进度不中断
  → 已完成的显示结果入口
```

### 7.4 服务重启

```text
服务停止时任务仍在 processing
  → 启动读取 summary-jobs.json
  → 标记 error / SUMMARY_INTERRUPTED
  → 笔记状态同步为 error
  → 任务中心显示「已中断，可重试」
  → 点重试 → 复用转写缓存 → 快速完成
```

### 7.5 取消与重试

```text
运行中 → 取消 → 确认
  → status=cancelling
  → 当前阶段检查到取消
  → 清理临时目录
  → status=cancelled，笔记=cancelled
  → 点重试
  → 原 job 重置为 queued
  → 复用已有转写缓存（如果有）
```

### 10.4 性能观测方法

准备 3 条公开视频：

- 2 条有字幕、时长相近。
- 1 条无字幕、需要 Whisper。

记录：

- 单条串行总耗时。
- 3 条并行总耗时。
- 每个任务的 `startedAt / finishedAt`。
- 转写峰值并发、LLM 峰值并发。
- 失败/重试次数。

目标不是承诺固定秒数，而是：

- 有字幕任务不再互相排队。
- 无字幕任务的音频下载、LLM 总结能与下一个转写重叠。
- 用户可以在等待期间继续添加任务，而不是被页面卡住。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| CPU/内存被 Whisper 打满 | 机器卡顿、转写更慢 | 默认 `SUMMARY_TRANSCRIBE_WORKERS=1`；开 2 路前评估内存；队列上限 20 |
| DeepSeek 限流 / 费用增加 | 429、失败、账单变高 | LLM 并发默认 4；429/5xx 退避重试；并发可调低 |
| 总结线程被转写等待占住 | 部分并发浪费 | 默认 3 路 + 1 路转写；实测阻塞明显时再拆阶段队列 |
| SQLite 并发写 | `database is locked` | 现有 WAL + 30 秒 timeout；同 URL 去重避免同一篇笔记并发写 |
| 服务重启丢任务 | 用户以为任务消失 | JSON 快照 + 中断状态 + 重试 + 转写缓存 |
| 刷新时批量解析未完成 | 解析中的本地行丢失 | 提示「解析完成入队前请保持页面打开」；后续可做服务端批量创建 |
| 多标签页重复通知 | 提示重复 | 本轮接受；后续用 BroadcastChannel 协调 |
| 桌面通知不可用 | 局域网 HTTP 无权限 | Toast + 标题角标始终可用；提示 localhost/HTTPS |
| 取消等待 LLM 返回 | 取消不够即时 | UI 显示「正在取消」；最长等待一个 HTTP timeout |
| 缓存/结果过期 | 重开任务无结果 | 任务卡片保留笔记链接；提示重新生成 |

## 13. 暂不做与后续扩展

- **统一下载任务中心**：批量链接同时下载视频并总结；需要下载任务列表、批量画质选择、下载完成提醒。
- **队列暂停/恢复/优先级**：适合任务很多时；需要调度器支持暂停信号和优先级排序。
- **服务端批量创建**：粘贴即入队，标题后台补全；需要总结流程 probe 元数据并处理笔记重命名。
- **多设备同步 / 用户体系**：当前是私人单机工具，不做登录和云端。
- **服务端 Web Push**：需要 HTTPS、Service Worker 和推送服务；本轮只做本地通知。
- **SQLite 任务队列**：如果未来需要多进程/多机，再考虑持久化队列和独立 worker。

## 14. 已采用的默认值

以下默认值已按当前环境（20 核 CPU、本地 Whisper、DeepSeek）实现，可通过环境变量调整：

- 总结任务并发 3。
- Whisper 并发 1。
- 文案并发 2。
- LLM 总并发 4。
- 活跃任务上限 20。
- 任务历史 24 小时 / 最多 50 条。
- 批量一次最多 12 条，解析并发 3。
- 桌面通知默认关闭。
- 批量采用「先解析标题再入队」。
